# RAG 完整說明

> 寫給已經在維護知識庫（Obsidian vault）、用過 coding agent 的人。
> 2026-08-06

## RAG 是什麼

RAG（Retrieval-Augmented Generation，檢索增強生成）解決的是一個根本問題：**LLM 不知道你公司的事**。模型訓練資料裡沒有 QBurger 的 POS SOP、沒有支付設備故障處理流程，你問它，它要嘛說不知道，要嘛編一個看起來很像的答案（幻覺）。

RAG 的做法一句話講完：**回答之前，先從你的知識庫裡把相關段落找出來，連同問題一起塞給模型，要求它「根據以下資料回答，並註明出處」。** 模型從「憑記憶考試」變成「開書考」。

## 為什麼不直接把整個知識庫塞給模型？

因為塞不下、也不划算。模型一次能讀的量（context window）有限，就算塞得下，每次問答都把幾百份文件全丟進去，又慢又貴，而且資料太多反而稀釋注意力、答得更差。所以核心工程問題變成：**幾百份文件裡，怎麼快速找出跟這個問題最相關的 5 段？**

關鍵字搜尋做不到這件事——使用者問「刷卡機沒反應怎麼辦」，SOP 裡寫的是「支付設備故障排除」，一個關鍵字都對不上。這就輪到向量檢索出場。

## RAG 的兩條管線

### 1. 建庫（Indexing）——文件進來時做一次

```
文件 → 抽出文字 → 切片（chunking） → 每片算 embedding → 存進向量資料庫
```

- **切片**：把長文件切成幾百字的段落。因為檢索的單位是「段落」不是「整份文件」——你要的是精準命中的那一段，不是整本手冊。
- **Embedding（向量化）**：用一個專門的模型把每段文字轉成一串數字（例如 1536 個浮點數），這串數字代表**語意**。神奇之處在於：意思相近的文字，向量在數學上就靠得近。「刷卡機沒反應」和「支付設備故障」字面完全不同，向量卻很接近。
- 向量連同原文存進資料庫（專用的向量庫，或像新版 SQL Server 直接原生支援 `VECTOR` 欄位型別）。

### 2. 問答（Query）——每次提問時執行

```
問題 → 算成向量 → 到庫裡找最近的 K 段（如 TOP 5）
     → 段落＋問題組成 prompt → LLM 生成答案＋附出處
```

「找最近的」就是算餘弦相似度（cosine similarity）——純數學運算，毫秒級。找到的段落原文放進 prompt，模型照著回答，並回報是根據哪幾段答的——這就是答案下面「參考來源」卡片的由來，也是 RAG 對企業最重要的特性：**答案可以被查證**。

## 跟「Claude Code 直接讀 vault」差在哪

用 coding agent 讀 Obsidian vault 回答問題，其實已經是「檢索增強」的一種——只是檢索方式不同：

| | Claude Code 讀 vault | RAG 系統 |
|---|---|---|
| 找資料的方式 | agent 自己開檔案、跟著 `[[連結]]`、grep 關鍵字，逐步翻找 | 向量相似度一次算出最相關段落 |
| 速度與成本 | 每次翻找燒很多 token，幾十秒起跳 | 檢索本身毫秒級，只付生成答案的錢 |
| 誰能用 | 裝了 Claude Code、會下指令的工程師 | 任何人開網頁登入就能問 |
| 規模 | 幾十份筆記還行，幾千份會翻不完 | 百萬段落也是一次查詢 |
| 權限 | 檔案系統權限，粗粒度 | 查詢時按部門/角色過濾，細粒度 |

兩者不衝突，而且是上下游：vault 是**知識的生產與治理**（分類、升格、複查——這是 RAG 系統自己不會長出來的東西），RAG 系統是**知識的配送**（讓全公司都查得到）。維護良好的 Markdown＋frontmatter 正是 RAG 建庫最理想的原料——metadata 可以直接變成檢索的過濾條件，比大家亂丟 PDF 的品質好一個檔次。

## RAG 的限制（誠實條款）

- **檢索不到就答不好**：知識庫裡沒有的東西，RAG 只能說不知道（這其實是優點，總比瞎編好）。
- **切片會切斷上下文**：一個步驟被切在兩段裡，檢索只命中一半，答案就殘缺。所以切片策略（大小、重疊比例）要調。
- **問法太模糊時向量也救不了**：「那個東西壞了怎麼辦」誰來都難。
- **它不會維護知識**：過期的 SOP 檢索出來照樣答——所以 `last_verified`／定期複查這類治理制度反而是 RAG 系統的稀缺配套。

## 對照實際的系統（KnowledgeHub）

上面每個概念對應到具體選型：

| 概念 | KnowledgeHub 的選型 |
|---|---|
| 文件解析 | PdfPig（PDF）／直接讀文字（Markdown） |
| 切片 | 500 字、10% 重疊 |
| Embedding | Gemini `gemini-embedding-001`（1536 維） |
| 向量庫 | Azure SQL 原生 `VECTOR(1536)`，`VectorDistance` 算餘弦距離取 TOP 5，前置部門過濾 |
| 生成 | Gemini flash，Semantic Kernel Agent 自行決定要不要查庫 |
| 呈現 | SSE 串流回前端，附參考來源卡片 |

再往上一層是 Agent 工具擴充：查知識庫只是工具之一，之後會接 EIP 待審助理等其他工具。
